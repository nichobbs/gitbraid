# GitBraid VS Code Extension — Code Review
**Date:** 2026-04-22
**Scope:** Post-remediation state (after commit 6998dc7 wave); ~9,700 lines TypeScript

---

## Overall Health Summary

The first remediation wave cleared all P0/P1 blocking issues: shell injection on the hot-path was addressed by the IGitRunner seam, the config schema reached v2 with hunk anchors, the extension activates correctly, and the test surface grew substantially. The extension is now shippable for early adopters. However, three areas carry residual risk before a stable public release: the `exec()`-based shell injection surface in `gitFunctions.ts` and `hunkRouter.ts` still exists alongside the safe `IGitRunner` path (an incomplete migration rather than a completed one), two public API methods are declared but not wired in the facade, and the bidirectional-sync feature flag is present but the reverse-copy implementation is not yet exercised by any test. Test coverage thresholds (55%/45%) remain well below the original 70%/60% goal. No issues found represent regressions from the prior wave.

---

## What Improved

- **IGitRunner / ProcessGitRunner seam** introduced: new subsystems (rebaseRecovery, stackCommands, prAwareness) all use spawn-based execution with no shell, and `FakeGitRunner` makes them unit-testable.
- **HunkRouter reconciler** (`_reconcileAssignments`, `detectOverlaps`) is fully implemented and wired into `routeFile`; drifted assignments are detected and logged rather than silently forwarded.
- **ConfigService** atomic writes (tmp + rename), 50ms debounce coalescing, and optimistic-concurrency retry loop are all in place.
- **Drag-and-drop reordering** is implemented on `BranchStackTreeProvider` — `handleDrag`/`handleDrop` and the `TreeDragAndDropController` interface are present and wired into the tree view.

## Findings

### 1. Incomplete exec() migration — shell injection surface remains open
**Severity: High**

`gitFunctions.ts` line 7 declares `const exec = util.promisify(child_process.exec)` and line 69 executes `exec('git ' + args, { cwd: repoRoot })` — a template-string command passed to a shell. `hunkRouter.ts` line 9 declares the same `exec` import, though `git apply` at line 271 already uses `child_process.spawn` with `shell: false`. The core `gitExec` helper in `gitFunctions.ts` therefore still executes arbitrary shell strings built from caller-supplied argument fragments.

**File references:** `src/gitFunctions.ts:7,69`; `src/hunkRouter.ts:9`

**Fix:** Complete the IGitRunner migration started in `src/gitRunner.ts`. Replace the `gitExec` private method in the `Git` class with calls to an injected `IGitRunner`, splitting the `args` string at the call sites into proper string arrays. The `exec` import at line 7 of `gitFunctions.ts` and line 9 of `hunkRouter.ts` should then be removed. The hard assertion on metacharacters already in place is a good backstop but is not a substitute for shell:false.

### 2. API facade missing pullBranch and syncBranch
**Severity: High**

`GitBraidExportedAPI` (the public extension API) includes `pullBranch` and `syncBranch`. `GitBraidApi` (`src/gitBraidApi.ts:208,217`) implements both. `GitBraidApiFacade` (`src/gitBraidApiFacade.ts:97–145`) is the object handed to third-party extensions via `vscode.extensions.getExtension(…).exports`, but it implements every other method except these two. Callers that obtain the facade and invoke `facade.pullBranch(…)` will receive a runtime `TypeError: facade.pullBranch is not a function`.

**File references:** `src/gitBraidApiFacade.ts:145` (end of class — two methods missing); `src/gitBraidApi.ts:208,217`

**Fix:** Add the two one-line delegates to `GitBraidApiFacade`:

```typescript
async pullBranch(branch: string): Promise<void> { await this._api().pullBranch(branch) }
async syncBranch(branch: string): Promise<void> { await this._api().syncBranch(branch) }
```

Add a compile-time assertion `const _: GitBraidExportedAPI = new GitBraidApiFacade(…)` to a test so this class of omission is caught by TypeScript in CI.

### 3. Bidirectional sync — reverse path not covered by tests
**Severity: High**

`workspaceSync.ts` lines 138 and 158 check the `gitbraid.bidirectionalSync` setting and wire up `_onWorktreeChanged`. The `_reverseSync` method at line 450 does copy content from the worktree path back to the primary workspace. However, there is no test in `workspaceSync.test.ts` or `workspaceSync.bus.test.ts` that enables the flag and exercises the reverse path through a fake bus. The generation-counter deduplication logic at lines 432–437 is therefore untested, meaning a subtle loop bug (worktree write → primary event → sync back to worktree → worktree event … ) would not be caught by CI.

**File references:** `src/workspaceSync.ts:422–479`; no corresponding test in `test/workspaceSync.bus.test.ts`

**Fix:** Add a test suite block in `workspaceSync.bus.test.ts` that sets `bidirectionalSync: true`, fires `onDidChangeWorktree`, and asserts: (a) the primary file is updated, (b) a second worktree event with generation > 0 is suppressed.

### 4. FileChangeBus ignores files.watcherExclude
**Severity: Medium**

`src/fileChangeBus.ts:61–64` creates a `createFileSystemWatcher('**/*')` with no glob exclusions. On VS Code 1.95+, the platform notifies watchers for all FS events before filtering. In a monorepo with `node_modules` or generated directories excluded via `files.watcherExclude`, the bus still receives and re-dispatches every event, potentially causing hundreds of spurious sync cycles per second.

**File references:** `src/fileChangeBus.ts:61`

**Fix:** Read `vscode.workspace.getConfiguration('files').get<Record<string, boolean>>('watcherExclude')` at construction time, build a negative-glob set, and skip events whose `relativePath` matches any excluded pattern before dispatching. Alternatively, pass the exclusion list to a secondary `RelativePattern` that the watcher constructor accepts in newer API versions.

### 5. ConfigService concurrent-window race window
**Severity: Medium**

`_detectDiskConflict` at `src/configService.ts:492` calls `fs.statSync` (synchronous) to read the file's `mtime`, then compares it to `_lastSeenMtimeMs`. The comparison happens inside `_writeNow`, but the actual write (`writeFile` + `rename`) happens several async ticks later at lines 471–472. There is no mtime re-check between the conflict-detection synchronous read and the rename. On a heavily loaded system or a shared network filesystem, a second window could write between the `statSync` and the `rename`, and the conflict would be silently overwritten.

**File references:** `src/configService.ts:460–483`

**Fix:** After the `rename` succeeds, re-stat the file and compare the new mtime to the pre-write mtime read at detection time. If they do not match (another writer raced), treat it as a conflict and loop. Alternatively, use a lock file (`local-config.json.lock`) created with the `wx` flag (exclusive open) to serialise writers.

### 6. scratch branch type undocumented and partially exposed
**Severity: Medium**

`configTypes.ts:24–28` defines `scratch?: boolean` on `BranchStackEntry` with a JSDoc comment describing the intended UX (parking area, SCM panel behaviour). The `gitbraid.addScratchWorktree` command at `src/extension.ts:907` creates and marks a scratch branch. However, the feature is not listed in the extension's `README`, the `package.json` command palette entry carries no description of the scratch semantic, and no walkthrough step covers it. The `configTypes.ts` JSDoc references "the SCM panel for scratch branches" but no special SCM rendering is in place — scratch branches display identically to normal branches.

**File references:** `src/configTypes.ts:24–28`; `src/extension.ts:907–921`

**Fix:** Either (a) implement the special SCM treatment documented in the JSDoc and add a walkthrough step, or (b) mark the feature experimental in the command palette description (`"(experimental)"`) and add a one-sentence note to `README.md`. The undocumented gap between the type definition and the runtime behaviour is the core issue.

### 7. extension.ts is 1,376 lines
**Severity: Medium**

`src/extension.ts` remains at 1,376 lines. Most of the reduction from earlier refactoring went into dedicated service files, but the command registration block is still inline — individual command handlers are 20–50 line closures defined directly in `activate`. This makes it difficult to unit-test individual commands and creates merge-conflict pressure.

**File references:** `src/extension.ts` (entire file)

**Fix:** Extract command handler blocks into a `src/commands/` directory, one file per domain (e.g., `branchCommands.ts`, `hunkCommands.ts`, `syncCommands.ts`). Each file exports a `registerCommands(ctx: ExtensionContext): vscode.Disposable[]` function. `extension.ts` then becomes a thin orchestration file under 300 lines.

### 8. Hunk reconciler does not emit a diagnostic for fuzzy-match drift
**Severity: Medium**

The T8 spec called for a user-visible warning when an assignment drifts to a fuzzy-matched position (score 0.5–0.9), distinct from the silent drop when no match is found. `_reconcileAssignments` at `src/hunkRouter.ts:215–228` handles three cases: exact hash match (silent), single fuzzy match (silently accepted), and ambiguous/no match (warn-and-drop). The single-fuzzy-match path at line 220 carries no user notification. A hunk that shifts by several hundred lines after a large rebase is silently re-assigned to whatever overlaps — the developer has no indication that the assignment may now be incorrect.

**File references:** `src/hunkRouter.ts:220–221`

**Fix:** Add a log-level warning (or, for interactive sessions, a `showWarningMessage`) when the fuzzy path is taken:

```typescript
log.warn(`HunkRouter: fuzzy-relocated assignment for hunk ${oldIndex} (${branch}) — ` +
  `was ${anchor.startLine}-${anchor.endLine}, now ${candidates[0].startLine}-${candidates[0].endLine}.`)
```

This is low cost and directly addresses the diagnostic gap noted in the original T8 spec.

### 9. Test coverage thresholds below target
**Severity: Medium**

CI enforces `--lines 55 --branches 45` (`.github/workflows/*.yml:72`). The original T61 goal was 70% lines / 60% branches. The current floor is 15 percentage points below on lines and 15 points below on branches. Several high-risk modules — `workspaceSync.ts` (555 lines), `extension.ts` (1,376 lines), `gitFunctions.ts` (354 lines) — are likely pulling the average down.

**File references:** `.github/workflows/` CI config (lines 72–74)

**Fix:** Raise the CI thresholds incrementally toward the T61 goal (e.g., 60%/50% immediately, then 65%/55% after the next sprint). Prioritise new tests for `workspaceSync.ts` bidirectional path (see finding 3), `gitFunctions.ts` (which has no `IGitRunner` test double yet), and the `extension.ts` command handlers once they are extracted (finding 7).

### 10. @typescript-eslint/no-floating-promises not enabled
**Severity: Medium**

`.eslintrc.json` includes `@typescript-eslint` as a plugin but does not enable `@typescript-eslint/no-floating-promises`. The codebase uses `void expr` as a suppression convention in several places, indicating awareness of the issue, but unawaited promises in event handlers and timeouts can cause uncaught rejections that swallow errors silently in production.

**File references:** `.eslintrc.json:8` (plugin declared, rule absent)

**Fix:** Add to `.eslintrc.json`:

```json
"@typescript-eslint/no-floating-promises": ["error", { "ignoreVoid": true }]
```

The `ignoreVoid: true` option preserves the existing `void expr` pattern for intentional fire-and-forget calls (e.g., `void this._reverseSync(…)` in `workspaceSync.ts:445`). Existing call sites that use `void` correctly will pass unchanged.

### 11. _floatingDirty not fully pruned on file deletion
**Severity: Low**

`workspaceSync.ts:289–299` handles file deletion via `_onDeleted` and calls `_floatingDirty.delete`. However, `_onDeleted` only prunes the entry if the deleted URI is inside the workspace root. If a file is deleted via the worktree path (e.g., a branch reset deletes the worktree copy), the worktree event goes through `_onWorktreeChanged`, not `_onDeleted`, and `_floatingDirty` is never pruned for that key. Over a long session with many branch resets, deleted files remain in the floating set indefinitely (up to the FLOATING_DIRTY_CAP hard limit).

**File references:** `src/workspaceSync.ts:289–299,422–448`

**Fix:** In `_onWorktreeChanged`, after the generation-counter check, also remove the `genKey` from `_floatingDirty` when the event comes from a delete (i.e., when `vscode.workspace.fs.stat` throws on the worktree path). Alternatively, filter `_floatingDirty` against the live `git status` output during the periodic background refresh already present in `seedFromGitStatus`.

---

### 12. No injection regression test suite for gitFunctions.ts
**Severity: Low**

`test/diffEngine.test.ts:270` carries a comment noting that `IGitRunner` tests cover shell-metacharacter safety, but these tests exercise the `diffEngine` path only. `gitFunctions.ts` routes through the old `exec`-based `gitExec` helper (see finding 1) and has no parallel injection test. There is therefore no CI signal if a future refactor re-introduces a metacharacter path.

**File references:** `test/diffEngine.test.ts:270`; `src/gitFunctions.ts:69`

**Fix:** Once `gitFunctions.ts` is migrated to `IGitRunner` (finding 1), add a suite in `test/gitFunctions.test.ts` that injects a `FakeGitRunner` recording all `run()` calls. Assert that branch names, file paths, and commit messages containing shell metacharacters (`; & | $( )`) reach `FakeGitRunner.run()` as literal string elements in the argv array, not shell-expanded values.
